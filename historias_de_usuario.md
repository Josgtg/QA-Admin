# Historias de usuario

Todos los criterios respetan lo que fija el documento de alcance: el usuario es el encargado de calidad, las mediciones se capturan a mano con evidencia, las técnicas se reparten en cuatro dimensiones (especificación, diseño, desarrollo y conformidad) y el índice de salud va de 0 a 100\.

Estas HU están descritas en el archivo de [miro](https://miro.com/app/board/uXjVEYn9byY=/).

# Release 1

El primer release deja listo lo básico: varios proyectos por periodo, un modelo de calidad aplicado y las técnicas de QA elegidas.

| ID | Historia de usuario | Prioridad | Puntos | Criterios de aceptación |
| :---- | :---- | :---- | :---- | :---- |
| HU-01 | Como encargado de QA, quiero subir la evidencia de que se revisó una métrica de calidad para asegurar su cumplimiento. | Media | 3 | Al registrar la revisión de una métrica, el sistema pide el valor medido, la fecha y la evidencia (enlace o archivo). Si falta el valor o la evidencia, no se guarda y se señalan los campos vacíos. Un valor fuera del rango de la métrica se rechaza con un mensaje claro. La revisión queda en el historial de la métrica con fecha, valor, evidencia y autor, y el estado de cumplimiento se actualiza. |
| HU-02 | Como encargado de calidad, quiero seleccionar un modelo de calidad ya predefinido y aplicarlo a mi proyecto, para aumentar las probabilidades de obtener un producto de mejor calidad. | Alta | 5 | El encargado ve los modelos predefinidos con su nombre, descripción y características. Al aplicar uno, el proyecto queda asociado a él y muestra sus características y métricas. Si el proyecto ya tiene mediciones, cambiar de modelo pide confirmación. El modelo aplicado aparece en el detalle del proyecto. |
| HU-03 | Como encargado de calidad, quiero que se me provea de modelos de calidad ya predefinidos, esto para reducir el tiempo que toma la definición de un modelo | Alta | 3 | Hay un conjunto de 4 modelos de calidad base compuestos de varias métricas de calidad. Cada métrica activada tiene una meta o umbral de cumplimiento. |
| HU-04 | Como encargado de QA, quiero ver el catálogo de técnicas de QA para implementar en mi proyecto y facilitar su seguimiento. | Alta | 8 | El catálogo base muestra 8 técnicas, dos por cada dimensión. Cada técnica muestra nombre, dimensión, tipo de control (verificación o validación) y descripción. El catálogo se puede filtrar por dimensión. El detalle de una técnica muestra su objetivo, su pregunta clave y la evidencia que se espera. |
| HU-05 | Como encargado de calidad, quiero seleccionar las TQA que se seguirán en el proyecto para aumentar las probabilidades de obtener un proyecto de calidad. | Alta | 5 | El encargado marca en el catálogo las técnicas que aplicará el proyecto. Las técnicas elegidas aparecen en el seguimiento, agrupadas por dimensión. Si una dimensión queda sin técnicas, se muestra un aviso, pero se puede guardar. Quitar una técnica que ya tiene evidencias pide confirmación, y esas evidencias se conservan. |
| HU-06 | Como encargado de QA, quiero ser capaz de seguir varios proyectos al mismo tiempo para aumentar mi eficiencia. | Alta | 3 | La vista principal lista todos los proyectos del encargado con nombre, periodo e índice de salud. Se debe registrar el equipo de trabajo y sus roles para cada proyecto. Desde la lista se entra al tablero de cualquier proyecto y se puede volver a los demás. Los datos de un proyecto nunca aparecen en otro. Si no hay proyectos, se invita a registrar el primero. |
| HU-07 | Como encargado de QA, quiero dividir mis proyectos por periodo, para facilitar la organización. | Alta | 3 | Todo proyecto tiene un periodo, y es obligatorio al registrarlo. Al elegir un periodo, solo se ven los proyectos de ese periodo. Sin filtro, los proyectos aparecen agrupados por periodo, del más reciente al más antiguo. Un periodo sin proyectos muestra un mensaje de lista vacía. |

# Release 2

El segundo release agrega el seguimiento: estado de métricas, pasos y evidencias de cada técnica, y la evolución de la salud del proyecto.

| ID | Historia de usuario | Prioridad | Puntos | Criterios de aceptación |
| :---- | :---- | :---- | :---- | :---- |
| HU-08 | Como encargado de calidad, quiero consultar el estado de las métricas seleccionadas para mi proyecto, para tomar decisiones informadas que aumenten la calidad. | Alta | 5 | Cada métrica muestra su último valor, su meta y su estado: cumple, no cumple o sin medición. Una métrica sin mediciones aparece como «sin medición» y no cuenta como cumplida. Desde cada métrica se puede ver su historial de mediciones con la evidencia de cada una. Las métricas que no cumplen se destacan para llamar la atención. |
| HU-09 | Como encargado de calidad, quiero consultar un catálogo base de metricas de calidad para estudiar crear un modelo de calidad a partir de ellas para seguir en mi proyecto. | Alta | 5 | Un modelo nuevo necesita nombre, descripción y al menos una característica con una métrica. Cada métrica muestra nombre, descripción, forma de medirla, unidad y rango esperado. El catálogo base es de solo lectura: el encargado no puede cambiar sus métricas. |
| HU-10 | Como encargado de QA, quiero subir la evidencia de que un paso de una TQA ha sido llevado a cabo para asegurar su cumplimiento. | Alta | 5 | Al registrar un paso, el sistema pide un enlace o archivo como evidencia, la fecha y un comentario opcional. Un paso no se puede marcar como completado sin evidencia. Un archivo con formato o tamaño no permitido se rechaza, indicando qué se acepta. El paso queda completado con fecha y autor, y su evidencia se puede abrir después. |
| HU-11 | Como encargado de QA, quiero ver los pasos completados y faltantes en una TQA para asegurar la conformidad. | Media | 3 | Cada técnica muestra sus pasos marcados como completados o pendientes. Se muestra el porcentaje de avance de la técnica (pasos completados entre pasos totales). Cada paso completado da acceso a su evidencia. Cuando todos los pasos están completados, la técnica aparece como cumplida. |
| HU-12 | Como encargado de QA, quiero ver los pasos o acciones necesarias para seguir una TQA y facilitar su seguimiento. | Alta | 8 | El detalle de cada técnica muestra la lista ordenada de sus pasos. Cada paso indica qué hay que hacer y qué evidencia se espera. Cada técnica muestra su pregunta clave, por ejemplo en Revisión de Código: si el código es limpio, sigue las reglas y funciona sin romper nada. Las 8 técnicas base tienen al menos un paso definido. |
| HU-13 | Como encargado de calidad, quiero consultar los detalles de un proyecto para conocer su equipo, periodo y configuración. | Media | 1 | El detalle muestra nombre, periodo, tipo de software, equipo con sus roles, modelo de calidad, métricas y técnicas. Lo que aún no está configurado aparece como «sin configurar», con un acceso para configurarlo. Desde el detalle se puede ir a editar el proyecto. |
| HU-14 | Como encargado de calidad, quiero consultar gráficas que representen el estado de salud del proyecto a lo largo del tiempo, para facilitar la detección de problemas. | Media | 5 | El tablero muestra una gráfica del índice de salud (0 a 100\) a lo largo del tiempo. Al pasar el cursor por un punto se ven la fecha y el valor exacto. Se puede limitar la gráfica a un rango de fechas. Con menos de dos mediciones, se avisa que aún no hay datos suficientes para ver la tendencia. Ante una caída del índice, se puede ver qué métricas o técnicas la causaron. |

# Release 3

El tercer release suma personalización (modelos y técnicas propios), búsqueda y filtros, y los reportes.

| ID | Historia de usuario | Prioridad | Puntos | Criterios de aceptación |
| :---- | :---- | :---- | :---- | :---- |
| HU-15 | Como encargado de calidad, me gustaría consultar las métricas de mi proyecto con filtros por conformidad o por importancia, para facilitar el monitoreo. | Baja | 3 | Se puede filtrar por conformidad: cumple, no cumple o sin medición. Se puede filtrar por importancia: alta, media o baja. Los dos filtros se pueden combinar. Si ninguna métrica coincide, se muestra «sin resultados» y una opción para quitar los filtros. |
| HU-16 | Como encargado de QA, quiero definir mi propias métricas de calidad para adaptar un modelo a mis necesidades  | Media | 5 | Un modelo nuevo necesita nombre, descripción y al menos una característica con una métrica. Las métricas nuevas deben de contar con con forma de medir, unidad y meta. No se aceptan dos modelos con el mismo nombre. El modelo propio aparece junto a los predefinidos y se puede aplicar a un proyecto. Un modelo que usa algún proyecto no se puede borrar; el sistema indica qué proyectos lo usan. |
| HU-17 | Como encargado de QA, quiero definir mi propia técnica de calidad para adaptarla a mis necesidades. | Baja | 8 | Una técnica nueva necesita nombre, dimensión, tipo de control, descripción y al menos un paso. Cada paso indica la evidencia que se espera. La técnica aparece en el catálogo marcada como propia y se puede elegir en un proyecto. Las 8 técnicas base no se pueden editar ni borrar. |
| HU-18 | Como encargado de QA, quiero ver un reporte rápido del estado del proyecto con motivo de análisis. | Media | 5 | En una sola pantalla se ven el índice de salud (0 a 100), el cumplimiento de métricas y el avance de técnicas por dimensión. Lo que necesita atención aparece primero: métricas que no cumplen y técnicas con pasos pendientes. Se muestra la fecha de la última medición o evidencia registrada. Si el proyecto aún no tiene datos, el reporte dice qué falta configurar o registrar. |
| HU-19 | Como encargado de calidad, quiero editar la información de un proyecto para corregir datos desactualizados. | Baja | 1 | Se pueden cambiar nombre, periodo, tipo de software y equipo, y los cambios se ven en todas las pantallas. No se guarda si queda vacío un campo obligatorio, y se señala cuál. Al cancelar, no se guarda ningún cambio. Editar el proyecto no borra sus mediciones ni evidencias. |
| HU-20 | Como encargado de calidad, quiero buscar rápidamente entre mis proyectos por nombre para encontrarlos más rápido. | Baja | 1 | Al escribir parte del nombre, la lista muestra solo los proyectos que coinciden, sin importar mayúsculas ni acentos. Si ninguno coincide, se muestra «sin resultados». Al borrar la búsqueda, vuelven a verse todos los proyectos. Si hay un periodo elegido, la búsqueda se hace dentro de ese periodo. |
| HU-21 | Como encargado de QA, quiero generar un reporte PDF para tener una vista compacta del estado del proyecto. | Media | 5 | Al pulsar «Exportar a PDF» se descarga un archivo con el nombre del proyecto y la fecha. El PDF incluye los datos del proyecto, el índice de salud, el estado de cada métrica, el avance de cada técnica y lo que necesita atención. Los datos del PDF coinciden con lo que muestra la aplicación en ese momento. El contenido se lee bien y no queda cortado en el ancho de la página. |
